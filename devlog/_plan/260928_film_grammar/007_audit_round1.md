## External and media claims

- The installed `ima2 video --help` confirms 1–15 s, 7 references and reference mode ≤720p. The [xAI reference-to-video contract](https://docs.x.ai/developers/model-capabilities/video/reference-to-video) independently states max 7 images, max 15 s for 1.5, and 720p for reference mode. These are current-source facts, with provider/account readiness still unverified. `--as-reference` is meaningful for exactly one ref in the installed CLI; 2–7 refs already select reference mode. 040 should specify that exact conditional rather than imply the flag is always required.
- FFmpeg's [paletteuse contract](https://ffmpeg.org/ffmpeg-filters.html#paletteuse) requires a 256-pixel palette image. The local 1-pixel dry run failed with that error. A `color`+`hstack` graph is feasible only if its output has exactly 256 pixels, appropriate format/timebase, and entries for the authored 2–6 colors. Those details and the rendered-pixel verifier are missing (blocker 8).
- The [FFV1 specification](https://ffmpeg.org/~michael/ffv1.html) calls the codec lossless and intra-frame. This proves codec properties, **not** byte/frame equivalence between a seek into source MP4 and a pretrimmed FFV1 intermediate. Timestamp origin, VFR, source pixel format, color range and cut-end rounding remain implementation/test obligations. 010:70 asks for visual equivalence but needs frame-ID/PTS and proxy/final output evidence for a VFR, nonzero-seek fixture.
- `src/stage/raster.ts:58–81` provides text masks and `src/qa/artifacts.ts:8–11` provides FFmpeg still extraction, so drawtext-free labels are plausible. 020:12,38 does not name the cell composition helper or assert the label pixels/index map agree; a JSON index alone would not satisfy “labels burned into each cell.” See blocker 10.

2. **High — generated hold calculation loses nonzero `in` and compiled-plan provenance.** Location: `040_generated_clips.md:10,16–18,23–24` (G-14); `006_architect_consultation.md:78`. Trigger: a 5 s clip, layer `in=4s`, span 2 s, no `out`. Impact: the plan's `span×speed` is 2 s and compared to 5 s duration, so it predicts no warning even though only 1 s remains and one second freezes. Materialization currently replaces the source with an ordinary video (`src/assets/resolve.ts:48–82`), and the proposed map does not name a RenderPlan/IR field or `.plan.json` deserialization path for source ID and probed duration; `<out>.render.json` can silently omit the warning. Fix: define `requested=min(span×speed, out−in when set)`, `available=max(0, probedDuration−in)`, held output frames from `(requested−available)/speed` at output fps; carry provenance/duration into serialized plan and runner or precompute stable warnings into plan. Test in-point, speed, out, cache hit and `.plan.json` replay. Verification: verified by current source flow and arithmetic.
