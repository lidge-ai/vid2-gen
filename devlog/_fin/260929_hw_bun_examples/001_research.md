## 1. ffmpeg hardware-accelerated encoding (2026)

### Detecting that a listed encoder actually works

`ffmpeg -encoders` only proves the encoder was compiled in; NVIDIA states explicitly that "the presence of these encoders in FFmpeg does not guarantee hardware acceleration" ([Remotion quoting the same](https://www.remotion.dev/docs/hardware-acceleration)). The reliable probe is a real tiny encode and checking exit code 0:

```
ffmpeg -hide_banner -loglevel error -f lavfi -i color=c=black:s=64x64:d=0.1 -c:v h264_videotoolbox -f null -
# vaapi variant:
ffmpeg -vaapi_device /dev/dri/renderD128 -f lavfi -i color=c=black:s=64x64:d=0.1 -vf format=nv12,hwupload -c:v h264_vaapi -f null -
```

Projects doing this: [ALVR's HW encoding test wiki](https://github.com/alvr-org/ALVR/wiki/FFmpeg-Hardware-Encoding-Testing) and [screencast](https://github.com/alexballas/screencast). Failure strings to match: `Cannot load libcuda.so.1` / `No capable devices found` (NVENC without driver/GPU, [nvenc.c](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/nvenc.c), [HandBrake #5588](https://github.com/HandBrake/HandBrake/issues/5588)), `Failed to initialise VAAPI connection`, `Impossible to convert between the formats` (missing hwupload / wrong pix_fmt), `Error while opening encoder` (bad option combo), and VideoToolbox's `-q:v qscale not available` above.

### Speed vs quality, and hardware decoding

HW encoders are several times faster but need more bitrate for equal quality; one 2025 HEVC test hit VMAF ~95 with NVENC in 15.1 s / 5,076 KB vs x265 in 35.0 s / 4,692 KB ([scottstuff.net](https://scottstuff.net/posts/2025/03/15/a-tale-of-two-encoders/)). Remotion reports HW output is "significantly larger by default" and suggests `--video-bitrate=8M` for 1080p H.264 parity ([Remotion](https://www.remotion.dev/docs/hardware-acceleration)). VAAPI CQP is not CRF-like and has no two-pass/lookahead ([VAAPI wiki](https://trac.ffmpeg.org/wiki/Hardware/VAAPI)).

Hardware decoding only pays off when frames stay on the device: CPU filters force `hwdownload`/`hwupload` round trips, and NVIDIA's guide keeps everything on GPU (`-hwaccel cuda -hwaccel_output_format cuda -vf scale_cuda`) precisely to "eliminate memory transfers" ([HWAccelIntro](https://trac.ffmpeg.org/wiki/HWAccelIntro), [NVIDIA guide](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/ffmpeg-with-nvidia-gpu/index.html)). For filter-heavy CPU pipelines (drawtext, overlay, xfade, zoompan) HW decode buys little; only `scale_cuda`, `scale_npp`, `overlay_cuda`, `scale_vt`, `scale_vaapi`, `vpp_qsv` run on-device ([ffmpeg-filters](https://ffmpeg.org/ffmpeg-filters.html)).

**Recommendation for vid2-gen:** keep software decode and CPU filters as the default path; offer HW *encoding* only. Map one abstract `quality` knob per backend: videotoolbox `-q:v` (Apple Silicon) else `-b:v`; nvenc `-rc vbr -cq N -b:v 0 -preset p5`; qsv `-global_quality N`; vaapi `-rc_mode CQP -qp N` plus mandatory `-vaapi_device` + `format=nv12,hwupload`; amf `-rc cqp -qp_i/-qp_p N -quality balanced`. Probe each candidate once with the 64x64 lavfi encode, cache the result, and print the ffmpeg stderr on failure.

## 2. How peer tools expose HW acceleration

| Tool | Flag / option | Values, default | Codecs and platforms | Source |
|---|---|---|---|---|
| **Remotion** (v4.0.228+) | CLI `--hardware-acceleration`, `renderMedia({hardwareAcceleration})`, `Config.setHardwareAcceleration()` | `"disable"` \| `"if-possible"` \| `"required"`; default `"disable"` (the HW page spells the default `"disabled"`; the CLI reference says `"disable"`, so check the installed types) | macOS VideoToolbox (ProRes 4.0.228, H.264/H.265 4.0.236); Linux/Windows NVENC H.264/H.265 from 4.0.484. `crf` is rejected with HW; use `--video-bitrate`, plus `--max-rate`/`--buffer-size`. Not on Lambda/Cloud Run. Verbose log prints `Encoder: h264_nvenc, hardware accelerated: true`. | [HW accel](https://www.remotion.dev/docs/hardware-acceleration), [CLI render](https://www.remotion.dev/docs/cli/render) |
| **HyperFrames** (HeyGen) | `render --gpu` | boolean, default off | "Hardware FFmpeg encoding (NVENC, VideoToolbox, AMF, VAAPI, QSV)". Separate `--browser-gpu`/`--no-browser-gpu` (default auto locally, off in Docker) for Chrome capture. Quality: `--quality draft|looks|delivery|standard|high` (looks = CRF 16 default), `--crf 0-51`, `--video-bitrate`; MOV is fixed ProRes 4444. | [CLI reference](https://hyperframes.heygen.com/packages/cli) |
| **Motion Canvas** | none exposed | FFmpeg exporter (`@motion-canvas/ffmpeg`) exposes only a "Fast start" toggle | no codec/encoder/HW options documented | [Rendering docs](https://motioncanvas.io/docs/rendering) |
| **Revideo** | none exposed | `settings.ffmpeg.ffmpegLogLevel` (default `error`), `ffmpegPath`; video is encoded via browser WebCodecs, ffmpeg only mixes audio | no HW encoder option documented | [Revideo docs](https://docs.re.video) |
| **editly** | `customOutputArgs` (JS) | any ffmpeg output args; default automatic H.264. `--fast` is a low-res preview, not HW | HW via pass-through only (e.g. `['-c:v','h264_videotoolbox']`) | [editly README](https://github.com/mifi/editly) |
| **auto-editor** | `--video-codec`, `-crf 0-63`, `--preset` | pass-through to ffmpeg | any ffmpeg encoder name incl. `h264_nvenc` | [auto-editor options](https://auto-editor.com/options) |
| **HandBrakeCLI** | `-e/--encoder` | `x264`, `nvenc_h264`, `nvenc_h265`, `vce_h264`, `vce_h265`, `qsv_h264`, `vt_h264` ... (list varies by build/OS); `--encoder-preset-list <enc>` | local `--help` is authoritative | [HandBrake CLI options](https://handbrake.fr/docs/en/latest/cli/cli-options.html) |

**Recommendation for vid2-gen:** copy Remotion's three-state enum (`disable | if-possible | required`) as `--hw-accel` rather than HyperFrames' boolean, because agents need an explicit "fail if not accelerated" mode for CI. Add `--encoder <ffmpeg name>` as an escape hatch (editly/auto-editor style), refuse `--crf` with HW encoders and steer to `--video-bitrate` (Remotion's rule), and emit the resolved encoder plus `hardwareAccelerated: true|false` in JSON output.

**Recommendation for vid2-gen:** commit source + tiny input assets only; gitignore `out/` (and `*.mp4`, `*.gif` outside a fixtures dir). Each `examples/<name>/` gets a README with: title, one-line "what it demonstrates", the exact `vid2 render ...` command, expected output (duration, size, fps, codec), and a hosted preview (release asset, user-attachment URL, or docs CDN), never a checked-in render. Keep a top-level `examples/README.md` table like editly's. If golden-output tests are wanted, put small fixtures under `tests/` in LFS and document `GIT_LFS_SKIP_SMUDGE=1` as HyperFrames does.
